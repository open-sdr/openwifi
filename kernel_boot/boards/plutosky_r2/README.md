# PlutoSky R2 (`plutosky_r2`)

XC7Z020 (`xc7z020clg484-2`) + AD9361. Unlike the other supported boards, this
one boots from **QSPI flash**, not from an SD card, so the release artefact is
a `.dfu` image written to `/dev/mtd3` rather than a partitioned SD image.

`devicetree.dts` is a static board description. It keeps the XC7Z020/AD9361
clock, SPI, GPIO, SD and DDR definitions and replaces the stock FPGA
peripherals with the OpenWiFi AXI DMA, OFDM and control blocks.

## Build

The FPGA side lives in `openwifi-hw/boards/plutosky_r2`. Build it first, then
point the Buildroot build at the resulting XSA:

```bash
OPENWIFI_XSA=/absolute/path/to/system_top.xsa ./buildroot-build.sh plutosky_r2 build
```

Output:

```
output/plutosky_r2/images/openwifi-plutosky_r2-qspi.dfu
```

`buildroot-external/support/mk-plutosky-r2-qspi-firmware.sh` packs the bitstream,
`zImage`, the device tree and `rootfs.cpio.gz` into a FIT image, capped at
`0x1e00000` (30 MiB) so it fits `/dev/mtd3`.

## Boot chain

There are two separate things here, and only one of them is exercised by the
normal build.

**The SD image's `BOOT.BIN`** is the U-Boot SPL that Buildroot produces
(`output/common/images/boot.bin`, about 139 KB), copied by
`assemble-board.sh` exactly as for every other board -- this board no longer
special-cases it. The R2 DDR and clock setup reaches that SPL through
`buildroot-external/support/prepare-board.py`, which extracts `ps7_init_gpl.c`
(12,896 lines, GPL-2.0, generated by Xilinx from the hardware description) out
of the OpenWiFi XSA and applies it to U-Boot as
`output/plutosky_r2/generated/uboot-patches/0001-board-ps7-init.patch`. So the
PS7 configuration from `openwifi-hw/boards/plutosky_r2/retarget_system.tcl` is
what would initialise DDR. **This path has not been booted on hardware**: the
board ships without an SD slot in use, and all testing was done over QSPI.

**The QSPI boot chain** lives at offset 0 in flash, in the 1 MiB
`qspi-fsbl-uboot` partition (`reg = <0x00 0x100000>` in `devicetree.dts`), and
is *not* produced by this build. The board currently boots with its factory
FSBL + U-Boot there. That vendor binary is deliberately **not** tracked in this
repository: it is not redistributable and its U-Boot part is GPL-2.0 with no
matching source.

`build_qspi_fsbl.tcl` and `build_qspi_boot.ps1` build a from-source
replacement: a Xilinx FSBL generated from the same XSA, packed with Buildroot's
U-Boot by `bootgen`. Both steps succeed and produce a well-formed 808 KB Zynq
boot image that fits the partition, but when it is written to offset 0 the
BootROM does not execute it -- the serial console stays completely silent, so
the image header is being rejected before the FSBL runs. The factory boot chain
is required until that is resolved. The scripts are kept here for that work and
for recovery.

Note that a full (non-SPL) U-Boot plus FSBL only fits the 1 MiB partition after
trimming U-Boot; see the `CONFIG_*` block at the end of
`buildroot-external/board/common/uboot.fragment`.

## Flashing

`flash_plutosky_r2_qspi.tcl` programs QSPI from offset 0 over JTAG using
`program_flash`. It refuses to run unless `OPENWIFI_FLASH_ACK=I_UNDERSTAND` is
set, because it overwrites the boot chain.

`restore_factory_qspi_boot.tcl` and `restore_factory_dfu.cmd` put the board
back to its factory firmware.

## USB OTG gadget

`buildroot-external/board/common/rootfs-overlay/etc/init.d/S42plutosky-r2-usb-gadget`
brings up RNDIS + ACM on the OTG port. Two details are load-bearing:

- **MS OS descriptors are published before the UDC is bound.** Kernel 6.12's
  `f_rndis` reports the interface as class 02 / subclass 06 / protocol 00, and
  no Windows INF claims the compatible IDs that Windows derives from that. The
  device shows up with Code 28 and no network adapter. Publishing MS OS
  descriptors makes Windows synthesise
  `USB\MS_COMP_RNDIS&MS_SUBCOMP_5162001`, which the in-box `rndiscmp.inf`
  claims.
- **`bcdDevice` is 0x0613, not the kernel default 0x0612.** Windows caches
  whether a device has MS OS descriptors under
  `usbflags\<VID><PID><bcdDevice>` and never asks again once the answer is
  cached as "no". Changing `bcdDevice` changes the key, so Windows re-queries.

`S43plutosky-r2-usb-console` starts a serial console on the same OTG port.

A DHCP server bound only to `usb0` hands out `192.168.2.10-20`. It runs from a
copy of `dhcpd` named `/tmp/dhcpd-usb0` because `wgd.sh` calls `killall dhcpd`,
and `killall` matches on `/proc/PID/comm`, which is the name of the executed
file. A symlink does not work: the kernel resolves it and `comm` is still
`dhcpd`. The board is `192.168.2.1` on that link. No router or DNS option is
advertised, because announcing a default gateway on a point-to-point debug
link would send the host's real traffic to a board that does not route.

## Known limitation

The RF front end is a TC1-1-13MX+ balun with no PA. Its passband rolls off
above 3 GHz, so only 2.4 GHz has been tested; 5 GHz is not expected to work on
this hardware.
